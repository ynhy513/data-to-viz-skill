# Desktop visualization routing

Use when Data to Viz, Data, Visualize, and web/artifact skills match the same task. Data to Viz supplies chart reasoning and caveat review; select one primary presentation workflow using the destination and the actual interaction. These are personal integration rules derived from installed plugin instructions, not changes to those plugins.

## Select the presentation owner

First preserve the user's requested destination. Advice-only requests do not require creating an artifact. A standalone file, existing project component, or full report does not become an in-conversation tool merely because it contains a chart or controls.

| Actual request | Primary presentation owner | Integration rule |
| --- | --- | --- |
| Standard quantitative chart, including date/category filters, series selection, tooltips, or inspection of supplied observations | Installed Data `visualize-data` workflow when applicable | Use its actual supported chart component, family schema, delivery path, and checker. Broad Visualize/D3 or web-library advice does not justify redrawing supported marks |
| In-conversation calculator/simulation that recalculates modeled outcomes, or a bespoke interactive explainer | Installed `visualize:visualize` workflow for the whole tool, including its charts | Load its complete instructions and relevant composition/control guides. It owns shared state, presentation, theme, accessibility, validation, and inline delivery; do not force its charts into a competing Data-owned UI framework |
| Full Data report/dashboard with coordinated charts or ordinary filters | Installed Data report/dashboard workflow and its selected destination | Controls alone do not make it a bespoke inline calculator. Use its public chart interfaces and layout; do not substitute an inline fragment or publish elsewhere without authorization |
| Chart or map component in an existing application/codebase | Existing project stack plus the installed web visualization router and narrow relevant specialists | Preserve framework/component ownership. If a Data-owned report/dashboard is the actual task, its component contract still applies. Inline conversation CSS, wrappers, and delivery syntax do not belong in the application's source |
| Scientific/publication figure or explicitly requested static PNG/PDF/SVG | Established plotting/export tools and the relevant artifact skill | Keep quantitative source, resolution, fonts, and requested editability. Do not convert a paper figure into an interactive inline output |
| Native editable workbook/deck/document | Installed spreadsheet/presentation/document workflow | Preserve native format and editability where requested; hand it reviewed data and chart decisions rather than changing the destination |
| Pure conceptual node/edge diagram with no quantitative encoding | Appropriate diagram workflow; Mermaid for a small static structure | Outside Data to Viz's analytical scope. A broad web-router description mentioning UML does not require building a browser app |

Load the selected presentation skill, relevant references, and any router-selected specialists genuinely needed, rather than every matching skill. For a genuinely composite deliverable, give each distinct part a clear owner and follow the parent workflow's composition contract. Do not combine competing theme/layout/component systems within one artifact.

## Two frequently confused cases

- **Filter:** selecting Online/Store from measured monthly revenue changes which observations are displayed. This stays on the standard Data chart route; a dropdown does not make it a calculator.
- **Model:** changing price or expected demand recalculates revenue/profit. An in-conversation scenario tool stays on the Visualize route even when its outputs are bars or lines. Label modeled quantities and validate the underlying arithmetic separately.

## Keep helpers and evidence with their owner

- A Data standard chart uses Data's renderer and checker, and its own preview/export helper when necessary. Do not substitute Visualize's similarly named helper or treat a host visualization content reference as proof that the Visualize workflow was invoked.
- A Visualize tool follows the installed Visualize validation workflow. If a mentioned checker is unavailable, use its documented actual-runtime preview fallback; do not invent flags or pass a Data checker over a different component contract.
- A preview page is temporary QA unless the user requested a standalone deliverable. Preserve the original inline fragment and deliver its native reference where supported. A working preview proves that preview's runtime, not final native inline placement.
- Follow the selected workflow's verification contract: inspect authored marks/interactions and meaningful missing/empty/reset states where required; respect documented guarantees for unchanged standard Page output instead of adding a universal browser check. Numerical fidelity remains separate. Successful routing, source validation, browser execution, and final host display are distinct evidence levels. Report failures at the level observed.
- Discover current skill paths and helper APIs from the installed catalog; do not hardcode plugin cache versions. Follow host constraints and explicit user requests if they differ. Change this integration skill rather than editing vendor plugin caches.
